# 接入与测试

## API 模型接入

可以，但通常需要一层由开发者编写的“宿主程序”或 agent runtime。模型 API 本身只负责一次次接收输入和返回输出；宿主程序负责：

1. 启动或连接 Open Watch Cinema MCP。
2. 读取 MCP 工具和 AI viewing skill。
3. 把工具说明交给模型。
4. 接收模型的工具调用请求，真正执行 MCP 工具。
5. 把结果送回模型。
6. 保存下一次调用仍然需要的对话上下文和待办决定；运行中的 MCP 会保存身份、房间绑定和游标。

所以“有一个 API key”并不等于 MCP 会自动常驻。只要宿主程序实现了 MCP client 与模型 API 的桥接，任何合适的 API 模型都可以使用这套影院工具。

## 宿主需要保留的上下文

每次 API 请求都可能是一次新的模型调用。影院会保存影片、房间、消息和按时间生成的材料，但不会替所有模型实现通用长期记忆。

API host 至少应在下一次调用前恢复：

- 最近对话或可靠的滚动上下文；
- 已做出的决定，例如“等待观众按下播放”；
- `mcp/SKILL.md` 中的观影规则。

运行中的 MCP 会后台保留身份、当前房间和游标。若宿主重启 MCP，新的进程会从 active room 的安全初始窗口重新开始。

## 源码包含哪些测试

普通观众启动影院时不会运行 `tests/`，正式播放也不依赖这些测试文件。删掉它们，`node server.mjs` 仍然可以启动。

它们留在公开源码仓库，是因为测试能证明并守住很多不该靠口头保证的行为：

- 转码失败时不会随便覆盖原影片；
- 影片文件清理和历史房间删除分别预览、确认；
- 房间结束后会变成只读；
- AI 不会读到播放头之后；
- tick 游标不会无故重复或跳过材料；
- UI、字幕和 MCP 契约在修改后没有悄悄坏掉；
- 其他开发者提交修改时可以在自己电脑上验证。

因此：`tests/` 属于**开源项目与开发版本**，不是普通运行依赖。以后若制作只给最终用户下载的精简安装包，可以不把 tests 放进安装包；但 GitHub 源码仓库保留它们更可信，也更方便维护。

## 运行检查

在项目根目录运行 `npm run check` 检查语法，运行 `npm test` 执行测试。`npm run smoke:room`、`npm run smoke:ai` 和 `npm run smoke:mcp` 分别用测试素材检查房间、AI 和 MCP 流程。

更多宿主细节见 [MCP 技术参考](MCP%20技术参考.md)。

## 项目目录和本地数据

| 位置 | 内容 |
| --- | --- |
| `server.mjs`、`public/` | 本地 HTTP 服务、片库、播放器、字幕和按时间显示的房间消息 |
| `src/media/`、`src/storage/` | 片源识别、兼容检测、视频分段传输、SQLite 房间和手记 |
| `observer/`、`src/preparation/`、`src/visuals/` | 画面与声音分析、可续做的观影包、分镜选帧 |
| `src/delivery/`、`mcp/` | 按播放位置交付资料、读取分镜和 MCP 工具 |
| `watch-bridge/` | 自动跟片、本机 Codex App Server 与 ChatGPT Listener 接入 |
| `local-data/` | `media/` 存放合集和影片，`影院记录/` 存放房间、名字和手记的 SQLite 数据库，`模型/` 存放可重复使用的模型资源 |
| `tests/`、`scripts/` | 自动检查、安装入口和开发工具 |
